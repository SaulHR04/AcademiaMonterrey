Employee API con MongoDB

El mismo CRUD del proyecto 15, con el motor cambiado por debajo. Mismos cinco verbos, mismas seis rutas — pero sin tablas, sin scripts SQL y con un id que deja de ser un número. Vas a probarlo todo desde la terminal y a ver exactamente qué se movió.

  • Java 21
  • MongoDB 8 en Docker

Paso uno

01 Requisitos

Aquí está la primera sorpresa: la preparación es mucho más corta que con MySQL. No hay usuario que crear, ni permisos que otorgar, ni base de datos, ni tabla.

  • [ ]Java 21 o superior java -version debe decir 21 o más.
  • [ ]Docker corriendo docker ps debe responder sin errores.
  • [ ]curl instalado curl --version. Viene de fábrica en macOS, Linux y Windows 10 en adelante.
  • [ ]jq — aquí sí es prácticamente obligatorio jq --version. Con MongoDB vas a necesitar extraer ids de las respuestas, y eso se hace con jq.

Levantar MongoDB

# crear el contenedor (solo la primera vez)
$ docker run --name mongo-8 -p 27017:27017 -d mongo:8

# las siguientes veces basta con arrancarlo
$ docker start mongo-8

Y ya está. No hay scripts SQL. Compáralo con el proyecto 15, donde había que crear el usuario springstudent, darle permisos, crear la base employee_directory y definir la tabla employee con sus cuatro columnas. Aquí MongoDB standalone no trae autenticación por defecto, y crea la base y la colección solas en el primer insert. La colección employees no existe hasta que guardas el primer empleado.

Ver los datos por dentro (opcional)

El equivalente de MySQL Workbench es MongoDB Compass. Pero el cliente de línea de comandos ya viene dentro de la imagen:

$ docker exec -it mongo-8 mongosh employee_directory
> db.employees.find()

Paso dos

02 Arrancar la aplicación

Desde la carpeta del proyecto 16:

# opción A — desarrollo
$ ./mvnw spring-boot:run

# opción B — empaquetar y ejecutar el jar
$ ./mvnw clean package -DskipTests
$ java -jar target/cruddemo-mongo-0.0.1-SNAPSHOT.jar

Este proyecto escucha en el 8081, no en el 8080. Es deliberado: así puedes tener corriendo al mismo tiempo el proyecto 15 (MySQL, puerto 8080) y este, y comparar las respuestas de ambos lado a lado. Está fijado en application.properties con server.port=8081.

Igual que antes: la terminal donde corre la app se queda ocupada mostrando el log. Abre una segunda para los curl.

Paso tres

03 Tu primera petición

La prueba de vida. Fíjate en el puerto.

$ BASE=http://localhost:8081/api/employees
$ curl -s $BASE | jq .
[]

Un array vacío es la respuesta correcta la primera vez. La colección todavía no existe porque nadie ha insertado nada. En MySQL habrías tenido una tabla vacía; aquí no hay ni tabla.

Si te salió Connection refused, la app no está arriba. Si tardó y luego falló con un timeout, el que no está arriba es MongoDB — revisa la tabla de errores.

Paso cuatro

04 El ObjectId: el cambio que lo cambia todo

Esta es la diferencia que más te va a afectar en la práctica. En el proyecto 15 el id era un int que MySQL asignaba con AUTO_INCREMENT: 1, 2, 3… podías escribir $BASE/1 de memoria.

En MongoDB el id es un ObjectId: doce bytes que el driver genera y que viajan como veinticuatro caracteres hexadecimales.

"id": "6a8740e9585111a500317cb2"

La consecuencia práctica es inmediata: no puedes adivinar un id. Cada vez que crees un empleado tienes que capturar el id que te devolvió la respuesta para poder usarlo después. Y eso se hace guardándolo en una variable de shell:

# crea el empleado Y guarda su id en la variable ID
$ ID=$(curl -s -X POST $BASE -H "Content-Type: application/json" \
  -d '{"firstName":"Ada","lastName":"Lovelace","email":"ada@gmail.com"}' | jq -r '.id')

$ echo $ID
6a8740e9585111a500317cb2

# y a partir de aquí lo usas en cualquier ruta
$ curl -s $BASE/$ID | jq .

Descomponiendo la línea clave: $( ... ) es command substitution — bash ejecuta lo de adentro y sustituye el resultado. jq -r '.id' extrae el campo id, y la bandera -r (raw) lo entrega sin las comillas del JSON. Sin -r la variable guardaría el id con comillas incluidas y la URL saldría rota.

Los ObjectId no son aleatorios del todo. Los primeros cuatro bytes son la marca de tiempo de creación en segundos. Por eso dos empleados creados con segundos de diferencia tienen ids que empiezan casi igual — y por eso ordenar por _id equivale, en la práctica, a ordenar por antigüedad.

Paso cinco

05 Las seis rutas

Las respuestas de abajo son reales, capturadas contra la app corriendo. Los comandos suponen que ya tienes $BASE y $ID definidos como en el paso 4.

GET /api/employees findAll()

Lista todos los empleados. Sin verbo explícito, sin cabeceras y sin cuerpo.

$ curl -s $BASE | jq .
[
  {
    "firstName": "Ada",
    "lastName": "Lovelace",
    "email": "ada@gmail.com",
    "id": "6a8740e9585111a500317cb2"
  }
]

Del lado del servidor, este método ya no ejecuta un SELECT escrito a mano: llama a employeeRepository.findAll(), que Spring Data implementó solo.

GET /api/employees/{id} getEmployee()

Trae un empleado concreto. Aquí es donde necesitas la variable: $BASE/1 ya no existe.

$ curl -s $BASE/$ID | jq .
{
  "firstName": "Ada",
  "lastName": "Lovelace",
  "email": "ada@gmail.com",
  "id": "6a8740e9585111a500317cb2"
}

El @PathVariable ahora es String employeeId, no int. Ese cambio de tipo se propagó por el controlador, el servicio y su interfaz — cinco archivos por un solo campo.

POST /api/employees addEmployee()

Crea un empleado nuevo. El cuerpo es idéntico al del proyecto 15.

$ curl -s -X POST $BASE \
  -H "Content-Type: application/json" \
  -d '{"firstName":"Ada","lastName":"Lovelace","email":"ada@gmail.com"}' | jq .
{
  "firstName": "Ada",
  "lastName": "Lovelace",
  "email": "ada@gmail.com",
  "id": "6a8740e9585111a500317cb2"
}

No mandes id. El método hace theEmployee.setId(null) antes de guardar. En JPA esto era setId(0); en MongoDB el equivalente de «esto es nuevo» es null. Y cuidado con la diferencia: si el id llega con valor, Mongo no falla — reemplaza el documento entero que tuviera ese id.

PUT /api/employees updateEmployee()

Actualiza un empleado por completo. El id sigue viajando dentro del JSON, no en la URL — igual que en el proyecto 15. Nota que ahora va entre comillas, porque es un String.

$ curl -s -X PUT $BASE \
  -H "Content-Type: application/json" \
  -d "{\"id\":\"$ID\",\"firstName\":\"Ada\",\"lastName\":\"Byron\",\"email\":\"ada.byron@gmail.com\"}" | jq .
{
  "firstName": "Ada",
  "lastName": "Byron",
  "email": "ada.byron@gmail.com",
  "id": "6a8740e9585111a500317cb2"
}

Aquí las comillas cambian de bando. Como necesitas que bash expanda $ID, el cuerpo va entre comillas dobles y las comillas internas del JSON se escapan con \". Con comillas simples, bash no expandiría la variable y mandarías el texto literal $ID.

PUT sigue siendo reemplazo total. Si omites email, se guarda como null. Para cambios parciales, PATCH.

PATCH /api/employees/{id} patchEmployee()

Actualiza solo los campos que mandas. Id en la URL, cuerpo con lo mínimo.

$ curl -s -X PATCH $BASE/$ID \
  -H "Content-Type: application/json" \
  -d '{"lastName":"King-Noel"}' | jq .
{
  "firstName": "Ada",
  "lastName": "King-Noel",
  "email": "ada.byron@gmail.com",
  "id": "6a8740e9585111a500317cb2"
}

Aquí las comillas vuelven a ser simples: el cuerpo no contiene ninguna variable que bash tenga que expandir. El id va en la URL, y ahí $ID se expande igual.

Sigue rechazando id en el cuerpo con «Employee id cannot be modified». Es una guarda de seguridad explícita, no un bug.

DELETE /api/employees/{id} deleteEmployee()

Borra un empleado. Sin cuerpo, y por lo tanto sin -H ni -d.

$ curl -s -X DELETE $BASE/$ID
Deleted employee id - 6a8740e9585111a500317cb2

Sin | jq .: el método devuelve un String, no JSON. Si se lo pasas a jq, revienta con parse error.

Paso seis

06 El ciclo CRUD completo

Todo encadenado, capturando el id automáticamente. Este bloque se copia y se pega tal cual: no tienes que escribir ningún id a mano.

# 0 · variable base y estado inicial
$ BASE=http://localhost:8081/api/employees
$ curl -s $BASE | jq .

# 1 · CREATE — el id se guarda solo en $ID
$ ID=$(curl -s -X POST $BASE -H "Content-Type: application/json" \
  -d '{"firstName":"Grace","lastName":"Hopper","email":"grace@gmail.com"}' | jq -r '.id')
$ echo "creado: $ID"

# 2 · READ
$ curl -s $BASE/$ID | jq .

# 3 · UPDATE total — comillas dobles para que $ID se expanda
$ curl -s -X PUT $BASE -H "Content-Type: application/json" \
  -d "{\"id\":\"$ID\",\"firstName\":\"Grace\",\"lastName\":\"Murray Hopper\",\"email\":\"grace.hopper@navy.mil\"}" | jq .

# 4 · UPDATE parcial
$ curl -s -X PATCH $BASE/$ID -H "Content-Type: application/json" \
  -d '{"email":"amazing.grace@navy.mil"}' | jq .

# 5 · DELETE y verificación final
$ curl -s -X DELETE $BASE/$ID
$ curl -s $BASE | jq .

Al terminar, el último GET debe mostrar lo mismo que el primero.

La trampa de la configuración en Spring Boot 4

Todos los tutoriales de MongoDB con Spring — y las respuestas de StackOverflow, y los cursos grabados antes de 2025 — te dicen que la conexión se configura así:

spring.data.mongodb.uri=mongodb://localhost:27017/employee_directory   # ← ya no funciona

En Spring Boot 4 esa propiedad quedó deprecada a nivel error desde la versión 4.0.0. El prefijo correcto perdió el data:

spring.mongodb.uri=mongodb://localhost:27017/employee_directory

Y lo peligroso es que no falla. Con el nombre viejo la aplicación arranca sin un solo error, acepta POSTs, devuelve GETs y todo parece perfecto. Lo que pasa por debajo es que Spring ignora la propiedad en silencio y se conecta a su valor por defecto, mongodb://localhost/test. Estás guardando y leyendo correctamente — pero en la base test, no en la tuya. Solo lo descubres cuando abres Compass y tu base no existe.

Para comprobar en qué base estás escribiendo de verdad:

$ docker exec mongo-8 mongosh --quiet --eval 'db.adminCommand({listDatabases:1}).databases.map(d=>d.name)'
[ 'admin', 'config', 'employee_directory', 'local' ]

Si en esa lista ves test en lugar de employee_directory, revisa el prefijo. La lección general va más allá de MongoDB: una propiedad mal escrita en Spring Boot no truena, se ignora. El silencio no es señal de que algo esté bien configurado.

El paquete que desapareció

Lo más llamativo es lo que no está. El paquete dao/ completo — la interfaz más su implementación con EntityManager, unas setenta líneas — se reemplazó por esto:

public interface EmployeeRepository extends MongoRepository<Employee, String> {
}

Una interfaz vacía. Spring Data lee los dos parámetros de tipo — la entidad y el tipo de su @Id — y genera la implementación al arrancar, con findAll(), findById(), save() y deleteById() ya resueltos. Si mañana necesitas una consulta propia, basta declarar el método siguiendo la convención de nombres:

List<Employee> findByLastName(String lastName);

y Spring Data la implementa a partir del nombre, sin que escribas la consulta.

Anatomía de un comando curl

Idéntica al proyecto 15 — curl no sabe ni le importa qué base de datos hay del otro lado.

PiezaQué hace
-ssilent. Oculta la barra de progreso.
-X MÉTODOFuerza el verbo HTTP.
-H "..."Agrega una cabecera, típicamente Content-Type: application/json.
-d '...'El cuerpo JSON.
-w "..."Imprime una plantilla al terminar, p. ej. %{http_code}.
| jq .Formatea el JSON. jq -r '.campo' extrae un valor sin comillas.

El $ del inicio no se escribe: es el prompt de tu terminal. Los botones «Copiar» ya lo omiten.

-d ya implica -X POST. Por eso en PUT, PATCH y DELETE el -X es obligatorio.

Comillas simples vs dobles. Simples cuando el JSON es literal; dobles (y escapando las de adentro) cuando necesitas que bash expanda una variable como $ID. Con MongoDB vas a usar las dobles mucho más que antes.

Ejercicios

Entrega los comandos que usaste junto con la respuesta que recibiste.

  1. Alta múltiple. Crea tres empleados guardando cada id en su propia variable (ID1, ID2, ID3). Lista la colección y comprueba que están los tres.
  2. Lee el reloj del ObjectId. Compara los tres ids que obtuviste. ¿Qué parte es casi idéntica entre ellos y por qué?
  3. PATCH quirúrgico. Cambia solo el email de uno. Demuestra con un GET que nombre y apellido no se movieron.
  4. El upsert de MongoDB. Haz un PUT con un id inventado pero con formato válido, por ejemplo aaaaaaaaaaaaaaaaaaaaaaaa. Mira qué pasó y explica en qué se diferencia de lo que esperarías en MySQL.
  5. Rompe el PUT. Manda un PUT omitiendo el campo email. Consulta después ese empleado y explica el resultado.
  6. Compara los dos proyectos. Levanta el 15 en el 8080 y el 16 en el 8081 al mismo tiempo. Haz el mismo POST en ambos y pon las dos respuestas lado a lado. ¿Cuál es la única diferencia?
  7. Limpieza. Borra todo lo que creaste y deja la colección vacía.
  8. Reto. Agrega a EmployeeRepository el método List<Employee> findByLastName(String lastName), expón un endpoint que lo use y pruébalo con curl. No escribas ninguna consulta.
